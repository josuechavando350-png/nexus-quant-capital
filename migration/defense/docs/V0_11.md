# 0.11.0 — ingesta de autenticación y vista compartida de incidentes

Esta entrega pertenece exclusivamente a `NQC-defensive`. No depende de SuperHunter ni modifica su rama, sus archivos o sus procesos. Tampoco activa producción.

## Recorrido implementado

`AuthLogMonitor` lee bytes reales de un archivo JSONL registrado. `OperationsStore` confirma en una misma transacción SQLite los eventos normalizados, las ventanas de detección, los casos y el cursor. Reabrir o competir con otro lector conserva el avance. Un fallo de inserción, capacidad o proceso antes del commit revierte el lote completo.

Los eventos llevan identidad de cliente, activo y fuente; tiempo declarado por el productor y tiempo observado; generación, identidad del archivo, intervalo de bytes y SHA-256 de la línea. Los casos referencian eventos concretos y la regla/configuración. El registro de fuente fija ruta, ámbito, umbral y ventana mediante un digest que debe conservar el operador.

La regla `auth_failure_burst_v1` abre un caso al alcanzar el umbral de fallos para el mismo principal y dirección dentro de la ventana configurada. Un acceso exitoso reinicia el episodio, pero no cierra una investigación. Los eventos atrasados se conservan con exclusión explícita de la regla; no se reinterpretan como eventos nuevos. Un fallo repetido no demuestra una intrusión ni identifica a un atacante. Esta entrega no revoca sesiones ni aplica bloqueos de red.

`capture-managed` consulta el estado verificado de `ManagedIntegrity` y lo proyecta en el mismo contrato de eventos y casos. Conserva referencias al recibo original. La importación es idempotente; una observación antigua no puede reabrir un caso con una secuencia posterior. La vista muestra ambas categorías para el mismo cliente/activo sin inferir causalidad. `source_reported_resolved` describe el estado comunicado por el motor; no significa recuperación completa de un equipo.

## Uso local

Desde `migration/defense`:

```bash
python3 -B tools/operations.py --root /ruta/nueva/operaciones init
python3 -B tools/operations.py --root /ruta/nueva/operaciones register-auth --source auth --tenant propio --asset servidor --log-root /ruta/logs --name auth.jsonl
```

El directorio padre debe existir y el directorio nuevo no debe existir. El archivo fuente debe existir. El registro devuelve `config_digest`: conservar el valor real para `poll-auth --source auth --config-digest VALOR`. Las rutas y `VALOR` del ejemplo son parámetros del operador, no valores incluidos en el código.

Formato de una línea aceptada, con `time_ns` como entero Unix en nanosegundos:

```json
{"schema":"nqc-auth-log-v1","time_ns":1793966400000000000,"outcome":"failure","principal":"alice","remote_address":"192.0.2.1"}
```

La línea es un ejemplo sintético. El productor debe emitir el esquema; todavía no hay adaptador nativo para SSH, Windows o proveedores de nube. Solo admite `success`/`failure`, principal con identificador simple e IP literal IPv4/IPv6. Una línea fuera del esquema genera `sensor.input_rejected`, con hash y motivo controlado, sin copiar su texto a la vista.

```bash
python3 -B tools/operations.py --root /ruta/nueva/operaciones poll-auth --source auth --config-digest VALOR
python3 -B tools/operations.py --root /ruta/nueva/operaciones events --tenant propio --asset servidor --limit 100
python3 -B tools/operations.py --root /ruta/nueva/operaciones cases --tenant propio --asset servidor --limit 100
```

Las consultas devuelven hasta 200 resultados por página. Para continuar eventos, `--after` usa la última secuencia; para casos, el último `case_id`. `capture-managed` exige `--managed-root`, `--manifest-digest`, `--tenant` y `--asset`. Es una importación explícita; no arranca procesos de fondo.

## Rotación y fallos

Al cambiar el inode, `poll-auth` rechaza el salto automático. El operador conserva el archivo anterior y detiene sus escrituras. Con `poll-auth --previous-name auth.old` drena su cola, incluso tras reiniciar. `rotate-auth --previous-name auth.old` exige llegar exactamente a EOF, comprueba el prefijo consumido y registra el cambio de generación junto al nuevo cursor. Después puede leerse el archivo activo. No se permite saltar una línea parcial pendiente.

Una reducción de tamaño o cambio del prefijo consumido se rechaza. Esto no demuestra que un productor nunca haya perdido eventos: cambios transitorios entre lecturas, `copytruncate` seguido de recrecimiento o pérdida antes de llegar al archivo no pueden excluirse con este sensor. La declaración de que el archivo anterior quedó sellado depende del operador y del productor.

Límites: archivo de 16 MiB; línea de 16 KiB; hasta 1.000 registros y 1 MiB consumido por lote; 1.000 fuentes, 100.000 eventos y 10.000 casos por almacén. Se relee el archivo completo para verificar el prefijo; el costo crece con su tamaño. La saturación rechaza la transacción y conserva el cursor. No hay borrado o retención automática. El tamaño SQLite físico no está limitado por estas cuotas lógicas.

## Evaluación reproducible

```bash
python3 -B tools/check_auth_pipeline.py
python3 -B -m unittest discover -s tests -p test_auth_log.py -v
```

La evaluación declara nueve escenarios sintéticos y etiquetas de necesidad de revisión. Produce 3 verdaderos positivos, 4 verdaderos negativos, 1 falso positivo y 1 falso negativo. El error benigno repetido abre caso; fallos repartidos entre direcciones no alcanzan el umbral por dirección. Precisión y sensibilidad son 0,75 exclusivamente en este conjunto pequeño, diseñado junto a la regla; no constituyen una estimación productiva ni evaluación independiente.

También comprueba rotación, reapertura sin duplicación y coexistencia con el caso de integridad y su recuperación. Registra tiempo de pared, CPU, memoria Python trazada y tamaño SQLite para 500 eventos sintéticos en una ejecución local. Ese resultado no establece un SLO ni superioridad frente a otro producto.

## Límites de confianza pendientes

- Es una herramienta local del operador. Los filtros de cliente/activo no son autenticación ni aislamiento ante un usuario con acceso directo a SQLite.
- Los hashes de eventos detectan cambios si se conserva el digest; no son firmas ni impiden reescritura por quien controla la base. Los casos de integridad conservan su fuente autenticada, pero el almacén operativo aún no tiene anclaje independiente.
- Los timestamps y resultados de autenticación son afirmaciones del productor. Un timestamp futuro o alterado puede reducir la evaluación posterior; las exclusiones quedan visibles.
- Evidencia referenciada por hash/rango no equivale a conservar una imagen forense del log. Debe retenerse el archivo original por una política externa.
- No se probó pérdida eléctrica, almacenamiento en red, carga productiva sostenida ni separación administrativa de clientes.
- No existe respuesta automática de autenticación ni integración productiva con Census. La siguiente entrega debe mejorar la cobertura evaluada y conectar una fuente nativa autorizada antes de habilitar acciones.
