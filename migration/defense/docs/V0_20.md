# 0.20.0 — reutilización de registros públicos verificados

Las verificaciones repetidas del receptor pueden reutilizar la reconstrucción de una versión idéntica del registro. Cada llamada vuelve a leer SQLite, compara todos los campos y bytes almacenados, exige el recibo externo esperado y verifica de nuevo la firma y los bytes del expediente. No se conserva un resultado de aceptación de expedientes en caché.

`VerifiedRegistry.from_bundle` ejecuta primero el verificador completo de 0.19. Su resultado conserva únicamente claves, estados, referencias y pins inmutables de esa versión. El constructor directo se rechaza, sus mapas son de solo lectura, sus valores internos son tuplas/bytes y el checkpoint expuesto es una copia. Esto previene modificaciones accidentales del objeto; no es aislamiento contra código malicioso que ya se ejecuta en el mismo intérprete.

`verify_registered` conserva su contrato y sigue haciendo una reconstrucción completa cuando recibe bytes nuevos. `RegistryMirror` mantiene como máximo una versión preparada por instancia. Antes de reutilizarla, comprueba los permisos y la identidad del almacén y relee la fila completa bajo transacción. Si cambia cualquier campo, vuelve a validar el contenido. La recepción de una revocación sustituye la versión y se serializa con la verificación. `clear_cache()` permite descartar explícitamente la referencia conservada.

Un objeto `VerifiedRegistry` retenido por el consumidor sigue representando su checkpoint histórico. No se convierte automáticamente en una vista actualizada. La frescura continúa limitada a versiones recibidas y referencias externas; la memoria caché no establece una autoridad temporal ni una custodia independiente.

## Comparación ejecutada

Se ejecutó el código publicado de 0.19 en un checkout separado y el candidato 0.20 en procesos distintos. Ambos recibieron exactamente los mismos archivos y base pública. Los almacenes y claves privados del emisor se retiraron antes de lanzar los verificadores. Se alternó el orden de ejecución en dos rondas; cada proceso hizo una primera verificación y doce repeticiones.

| Eventos del registro | Mediana repetida 0.19 | Mediana repetida 0.20 | Cociente observado |
|---|---:|---:|---:|
| 512 | 314.35 ms | 1.34 ms | 234.0 veces |
| 4.096 | 2.478 s | 6.30 ms | 393.2 veces |

Los informes canónicos fueron idénticos en las 104 verificaciones. Los datos completos, primeras llamadas, CPU, máximos de memoria y hashes de los módulos están en `REGISTRY_CACHE_CHECK.json`. El tiempo de la primera llamada sigue incluyendo la reconstrucción completa. Los historiales de volumen se prepararon con inserción masiva explícita de eventos firmados; esta medición no representa miles de escrituras por API ni tráfico productivo.

Las mediciones se realizaron en Python 3.12.14/Linux, mientras otra prueba prolongada utilizaba el mismo host. No son un SLO ni un rendimiento universal. La lectura de los bytes almacenados continúa creciendo con el tamaño del registro; el límite sigue siendo 4.096 eventos y 32 MiB por paquete.

Reproducir con un checkout local confiable de 0.19:

```bash
python3 -B tools/check_registry_cache.py --baseline /ruta/al/checkout-019/migration/defense
python3 -B -m unittest discover -s tests -p test_registry_cache.py -v
```

Se añaden quince pruebas de caché: reconstrucción inicial, almacenamiento releído, corrupción de bytes/metadatos, identidad/permisos, recibos externos, firma/expediente/pins por llamada, objetos inmutables, liberación de referencias y revocación. Se conservan además las pruebas existentes de concurrencia, bifurcaciones, retroceso total de base y terminación real de procesos.

Esta mejora amplía componentes existentes. Conserva 22 componentes parciales, 78 pendientes y 0 completos; las disciplinas todavía no tienen aceptación de alcance completo. La prueba prolongada del código congelado de 0.19 sigue en curso al preparar esta publicación y se informará por separado al terminar.
