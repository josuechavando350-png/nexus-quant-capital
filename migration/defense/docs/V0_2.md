# Versión 0.2.0 — cambios comprobados

## Fallo corregido

La versión 0.1.0 consultaba el reloj antes de esperar la transacción SQLite. En una espera, el token podía evaluarse con una hora anterior a su vencimiento. La versión 0.2.0 consulta el reloj después de obtener el bloqueo y verificar la auditoría. Una prueba comparativa ejecutó ambas versiones sobre archivos y bloqueos reales, avanzando un reloj controlado hasta la expiración: 0.1.0 admitió; 0.2.0 rechazó `invalid_token`. Los resultados están en `CLOCK_LOCK_REGRESSION.json`.

## Funcionalidad añadida

- **Recibos causales:** el motor guarda política, sujeto, identificador, hechos observados, hashes, errores de lectura, tiempos y comprobaciones ordenadas. La respuesta incluye `receipt_sha256`; el recibo completo se consulta solo por la API/CLI local. No contiene el token.
- **Presupuesto de cuarentena:** el límite se evalúa y aplica en la misma transacción que consume el token y escribe la auditoría. Una prueba con cuatro procesos nuevos y seis activos alterados confirmó dos cuarentenas y cuatro rechazos con límite dos.
- **Vigencia de evidencia:** exige la lista completa y ordenada de artefacto/señuelos, rechaza observaciones fuera de orden y duraciones superiores a la política. El piso de reloj se conserva entre reinicios. También se comprueba al liberar una cuarentena.
- **Verificación independiente:** valida manifiesto ZIP, política fijada, cadena HMAC, checkpoint externo y reproducción de las decisiones. Una prueba con una decisión incorrecta pero reautenticada con la clave de prueba también fue rechazada por inconsistencia lógica.

## Compatibilidad

Las políticas v1 se conservan byte por byte y usan controles explícitos de esta versión: antigüedad máxima de 5 segundos y máximo de cuarentenas igual al número de activos. Las políticas v2 incorporan `evidence_max_age_seconds` (0–300) y `max_quarantined_assets` (0–número de activos). El inicializador genera v2. Cambiar el digest exige otro estado; no hay migración silenciosa de la configuración.

La respuesta de inspección añade `receipt_sha256`; los clientes con validación estricta deben reconocerlo. El ZIP de auditoría añade `policy.json`. El nuevo verificador exige ese formato. Los registros históricos sin recibo se autentican y se cuentan como `legacy_unreplayed_decisions`; nunca se presentan como decisiones reproducidas.

Los estados HTTP son 200 para admisión, 423 para cuarentena, 429 para cuota, 409 para repetición o presupuesto agotado y 503 para evidencia vencida o fallo de reloj. Los errores de autenticación siguen siendo 401.

La evidencia local es puntual y depende del proceso y reloj del operador. Reproducir un recibo demuestra coherencia de la decisión con los hechos registrados, no la veracidad independiente de esos hechos. Sigue pendiente un anclaje de auditoría fuera del host.
