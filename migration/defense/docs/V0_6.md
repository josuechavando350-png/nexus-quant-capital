# 0.6.0: archivo local verificable antes del checkpoint

`ArchiveStore` conserva páginas por su SHA-256 y publica un manifiesto JSON canónico al completar el intervalo. El manifiesto fija política, identidad de clave de auditoría, checkpoints inicial/final, orden y tamaño de páginas, número de registros y hash encadenado de páginas. Se rechazan campos extra, hashes usados como rutas no válidos, intervalos incoherentes y formatos no canónicos.

`publish_local` escribe en un temporal exclusivo, sincroniza los bytes, crea el nombre final atómicamente mediante enlace sin reemplazo, retira únicamente su temporal y sincroniza el directorio. Un objeto existente se compara byte por byte antes de reutilizarlo y también se sincroniza. Una colisión de nombre temporal no elimina el archivo ajeno. Los fallos pueden dejar objetos sin manifiesto o temporales de una terminación abrupta; no se reparan ni se borran automáticamente.

`prepare` verifica cada página, la publica, la relee y comprueba su hash. Solo después de verificar el intervalo completo publica el manifiesto. Antes de responder vuelve a abrir el manifiesto y todas las páginas. `verify` repite esa comprobación sin necesitar la base de datos del motor. Los límites por intervalo son 4.096 páginas y 256 MiB de páginas; el manifiesto admite hasta 1 MiB. La memoria no acumula el contenido de todas las páginas.

`finalize` alimenta al testigo con las páginas leídas del archivo. El testigo verifica el intervalo y compara su recibo esperado bajo bloqueo antes del commit. La confirmación del archivo comprueba que el registro histórico del testigo coincide exactamente en identidad, intervalo, cantidades y hash encadenado. Un reintento puede recuperar el mismo registro después de perder la respuesta, incluso si hubo avances posteriores, sin modificar el checkpoint actual. Si otro proceso registró una paginación diferente, el reintento se rechaza aunque termine en el mismo checkpoint.

`ArchiveStore.capture` conecta exportación del motor, archivo y finalización del testigo. La CLI del motor añade `archive-audit`, con testigo configurado, `--archive-root`, `--target`, `--expected` y `--limit`. La herramienta `archive_audit.py` permite crear el almacén, preparar archivos existentes, verificar y finalizar. Su salida opcional de recibo usa creación sin sobrescritura y acepta un reintento de bytes idénticos.

Validación: 30 pruebas nuevas, 203 del paquete y 9 de aislamiento. Incluyen páginas faltantes/adulteradas, manifiesto y transcript alterados, reordenamiento, límites, permisos/enlaces, deduplicación concurrente, confirmación concurrente, recuperación tras reapertura y tras avances posteriores, fallo diferido de commit SQLite, conflictos de nombres y CLI. Los fallos de sincronización de archivo/directorio/manifiesto se inyectan explícitamente mientras se ejecuta el resto de la E/S real; no son pruebas de corte eléctrico físico.

El manifiesto real de NQC se consume dos veces: se archivan y releen seis páginas en dos intervalos antes de avanzar el testigo a los registros 3 y 6. Otra aceptación archiva una admisión de código real, reabre sus archivos, recupera una confirmación sin duplicarla y comprueba que la corrupción posterior impide afirmar disponibilidad. Las pruebas no modifican las fuentes originales de NQC.

Límites: el almacén es local y la API no sobrescribe contenido, pero el mismo usuario o un administrador pueden alterarlo. La verificación prueba disponibilidad en ese momento, no permanencia futura. No hay réplica independiente, monitor continuo, WORM, cuota global, inventario entre intervalos, eliminación de huérfanos ni retención. El historial original permanece completo. El testigo directo de 0.5.0 sigue disponible y por sí solo no acredita almacenamiento; para esta garantía local se usa la ruta de archivo.
