# 0.12.0 — adaptadores de resultados OpenSSH

Esta entrega se publica únicamente en `NQC-defensive`. Conserva el código de SuperHunter separado y no activa servicios, sesiones SSH ni respuestas automáticas.

## Recorrido ejecutable

El lector existente admite dos formatos adicionales: texto de OpenSSH con prefijo de fecha RFC3339 y exportaciones JSON de journald, una entrada por línea. Los bytes pasan por el mismo cursor transaccional, contrato de eventos, regla `auth_failure_burst_v1` y consulta de casos. No se genera una segunda cadena de detección aislada.

El registro fija formato y host esperado en el digest de configuración. Las fuentes JSONL anteriores conservan su configuración y sus pins sin cambios. Los adaptadores exigen nombres de proceso `sshd` o `sshd-session`; host distinto, campos incompatibles o fecha ambigua producen un registro de calidad y no aportan fallos al detector.

`Accepted` y `Failed` se interpretan solo para métodos admitidos y mensajes completos. `Partial`/`Postponed`, mensajes PAM, desconexiones y avisos aislados de usuario inválido quedan como `sensor.unclassified`. Esto evita contar dos fallos a partir del aviso de usuario inválido y su resultado final. Los detalles adicionales de claves/métodos no se copian a los eventos; se conserva el hash del mensaje.

## Configuración

Desde `migration/defense`, sobre un almacén local previamente creado:

```bash
python3 -B tools/operations.py --root /ruta/operaciones register-auth --source ssh --tenant propio --asset servidor --log-root /ruta/logs --name auth.log --format openssh-syslog-rfc3339 --expected-host mi-servidor
```

Usar el `config_digest` real devuelto con `poll-auth`. Para un archivo exportado de journald, elegir `--format openssh-journal-json`. No se consulta journald directamente ni se cambia la configuración del servidor. El operador proporciona archivos autorizados y el host exacto esperado.

Texto soportado: fecha con año, zona horaria conocida, hasta nueve decimales, host y `sshd[PID]:` o `sshd-session[PID]:`. Se rechazan timestamps sin año/zona y `-00:00` —offset desconocido—; no se adivinan fecha o zona. No se admiten segundos intercalares, fechas anteriores a Unix epoch, nanosegundos fuera de int64 ni más de nueve decimales. Este es un subconjunto de RFC3339 en un prefijo syslog, no un parser universal de RFC5424.

JSON de journald: exige `MESSAGE`, `__REALTIME_TIMESTAMP`, `__CURSOR`, `_BOOT_ID`, `_HOSTNAME`, `_COMM` y `_PID` como cadenas. Convierte los microsegundos de recepción de journald a nanosegundos sin usar coma flotante. Valores múltiples/binarios en esos campos y claves JSON repetidas se rechazan. Los eventos declaran la fuente y resolución del timestamp; la resolución no es una garantía de exactitud del reloj.

## Identidad y repetición

Para journald se combina el boot ID con el cursor opaco; su hash identifica la entrada dentro de la fuente registrada. Reexportarla registra `sensor.duplicate`, ligado al primer evento, sin volver a alimentar la regla. Reutilizar la identidad con contenido normalizado distinto registra `ssh_native_identity_conflict` y tampoco participa en la detección. La deduplicación comparte transacción con los eventos y el cursor; sobrevive a reinicios y rotación.

Se agrega la tabla local `native_records` de forma aditiva bajo transacción. Se preservan los eventos, fuentes y cursores anteriores. La deduplicación no cruza registros de fuente diferentes; dos fuentes que cubran el mismo journal requieren coordinación externa. El texto syslog no aporta identidad nativa estable: se protege por el cursor/rango del archivo, sin afirmar deduplicación entre copias independientes.

## Evidencia y evaluación

```bash
python3 -B tools/check_openssh_pipeline.py
python3 -B -m unittest discover -s tests -p test_openssh_log.py -v
```

La aceptación usa 12 escenarios escritos para esta entrega, separados del conjunto de nueve de 0.11. Comprueba resultados esperados de parsing/calidad, referencias del caso y reapertura sin duplicación. Son fixtures de formatos nativos basados en documentación/código oficiales; no son capturas de un servidor productivo ni evaluación independiente. No se ejecutaron intentos de acceso ni se arrancó un daemon. El entorno dispone de OpenSSH, pero no se alteró su infraestructura local para probarlo.

Las 31 pruebas nuevas cubren resultados finales/parciales, IPv6, métodos, host/proceso, precisión temporal, registros ambiguos, deduplicación, conflictos, errores de escritura, rotación, migración aditiva y CLI. Se conserva la evaluación anterior: la regla sigue pudiendo alertar por errores benignos repetidos y sigue sin detectar el patrón repartido entre direcciones. No se retoca esa métrica para presentar los adaptadores como mayor precisión de detección.

## Límites

- Los campos de host, proceso y resultado son afirmaciones del registro/exportación. `origin_authenticated: false` permanece explícito: ni el formato ni el hash demuestran el origen.
- No se implementa transporte autenticado, firma de origen, anclaje independiente ni adquisición de toda la evidencia del host.
- Se mantienen los límites de archivo/lote/capacidad y el protocolo explícito de rotación de 0.11. Los logs sin formato admitido quedan visibles como calidad o mensajes no clasificados.
- Nombres de usuario fuera del subconjunto ASCII admitido, nombres posiblemente truncados de 100 caracteres y métodos desconocidos no se convierten en éxitos/fallos. Su ausencia de evaluación debe considerarse un punto ciego.
- La cadena de autenticación llega a detecciones y casos; no revoca sesiones ni recupera servidores. La cadena de integridad conserva su recuperación local.
