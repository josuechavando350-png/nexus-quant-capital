# 0.17.0 — expediente de revisión verificable fuera del almacén

Entrega exclusiva de `NQC-defensive`. `review_dossier` une el paquete de evidencia existente, el historial del caso, los cambios de credenciales y el registro temporal en un expediente JSON canónico. Su verificador reconstruye el resultado sin abrir la base operativa ni los archivos de origen.

## Recorrido y evidencia

1. El custodio aporta pins externos de política, caso, configuración, evidencia y checkpoints esperados.
2. Se vuelve a verificar el paquete de evidencia.
3. Dentro de una transacción operativa se verifican credenciales, revisión, reloj y checkpoints. Se captura una vista coherente de esos registros.
4. Fuera de la transacción se verifica el expediente completo y se publica en un directorio privado, sin reemplazar contenido diferente. Se relee y verifica antes de devolver éxito.
5. Otro proceso verifica los bytes exportados, sus pins y una clave de auditoría aportada expresamente. Puede hacerlo después de retirar los logs, la política y la base originales.

El expediente conserva los payloads canónicos y las marcas HMAC originales. No vuelve a firmar ni reescribe registros antiguos. La evidencia incrustada conserva su hash original; no puede reemplazarse por otro paquete distinto aunque ese otro paquete sea válido por sí mismo.

El exportador necesita la clave administrativa porque el expediente contiene la política completa y su historial de credenciales, incluidos actores de otros ámbitos de esa política. Una credencial ordinaria de revisor no autoriza esta exportación. Los campos de claves y tokens secretos no se añaden al expediente; los registros originales y los motivos escritos por personas pueden contener información sensible y requieren manejo privado.

## Informe derivado

`verify_dossier` devuelve un informe JSON reproducible con:

- Registros que activaron la regla, sus IDs y el hash de su evidencia.
- Estado de detección original, hash del caso y estado reconstruido de revisión.
- Checkpoints de revisión y credenciales, con referencias de cada acción al registro que la contiene.
- Estado temporal incluido y mínimo externo contrastado, cuando se ha configurado caducidad.
- Valoración marcada explícitamente como `analyst_claim`, enlazada a la revisión donde se registró.
- Límites explícitos de origen, identidad, disponibilidad y custodia.

No se convierte una valoración benigna en un hecho técnico certificado ni una secuencia de fallos de autenticación en prueba automática de intrusión. El informe describe el snapshot registrado; no comprueba que represente el estado más reciente de un sistema en funcionamiento.

## Verificación compartida

`verify_credential_rows` y `verify_case_rows` contienen las mismas reglas que usan las lecturas del almacén. `ReviewPolicyData` valida los bytes de política y la clave externa sin acceder al sistema de archivos. `ReviewClock.verify_row` permite comprobar el registro temporal sin una conexión SQLite.

El verificador offline del expediente no consulta el reloj actual, bases, red ni rutas contenidas en el documento. La CLI sí lee los tres archivos explícitos indicados por el operador: expediente, pins y clave. No necesita directorio de política ni base operativa.

Los historiales antiguos conservan las reglas v1/v2 ya soportadas. Se comprueban permisos, transiciones, expiración histórica, HMAC, secuencia, alcance y vinculación de evidencia. Un historial parcial o un checkpoint de otro estado se rechaza.

## Pins externos

El archivo de pins exige exactamente:

| Campo | Referencia esperada |
|---|---|
| `tenant`, `asset`, `case_id` | Ámbito y caso seleccionados |
| `case_digest`, `config_digest` | Pins del caso y registro de fuente usados al preservar evidencia |
| `evidence_digest` | Hash del paquete de evidencia preservado |
| `policy_digest` | Hash de la política de revisores |
| `case_checkpoint` | Checkpoint de la revisión que se quiere exportar |
| `credential_checkpoint` | Checkpoint del registro de credenciales que se quiere incluir |
| `minimum_clock_ns` | Instante mínimo conservado por el operador, o `null` si no hay control temporal configurado |

Los checkpoints mantienen el formato `{"revision": ..., "head": ...}` de las herramientas existentes. Se exige al menos una revisión del caso. Cuando hay reloj configurado, su observación debe cubrir el mínimo externo y el historial incluido. El mínimo es una expectativa del operador; no acredita por sí mismo una hora independiente.

El hash del expediente se devuelve al capturarlo y se aporta separadamente al verificarlo. No se toma como confiable un hash declarado dentro del propio paquete.

## CLI

Desde `migration/defense`:

```bash
python3 -B tools/review_dossier.py capture --help
python3 -B tools/review_dossier.py verify --help
```

`capture` requiere `--pins-file`, `--audit-key-file`, `--operations-root`, `--policy-root`, `--policy-digest`, `--evidence-file` y `--output`. El directorio padre de salida debe ser privado. Un nuevo snapshot debe usar otro archivo de salida; se puede comprobar una publicación anterior mediante su hash retenido.

`verify` requiere `--pins-file`, `--audit-key-file`, `--dossier-file` y `--dossier-digest`. Produce el informe JSON por salida estándar; un rechazo devuelve código 2 y una causa controlada.

La verificación todavía exige la clave HMAC de auditoría, cuyo poseedor puede generar registros. Por ello no es una firma pública ni un testigo con custodia independiente. El ejecutor del verificador debe pertenecer al ámbito confiable que ya custodia esa clave. La independencia del proceso respecto de la base no equivale a independencia de confianza.

## Límites y pruebas

Hasta 32 MiB de expediente, 16 MiB de payloads de historial, 8 MiB de evidencia, 4.096 cambios de credenciales y 1.000 revisiones del caso. Un exceso se rechaza; no se elimina silenciosamente un prefijo o parte de la evidencia. Estos límites acotan datos aceptados, no constituyen una cuota física de memoria ni un SLO.

La exportación puede confirmar una nueva observación local del reloj aunque falle después la publicación del archivo. No cambia checkpoints de revisión/credenciales ni autoriza respuesta sobre activos. Una modificación posterior del sistema no cambia el significado histórico del expediente; para exigir otra versión se necesitan sus nuevos pins.

Comprobaciones:

- 38 pruebas del expediente: CLI, eliminación de fuentes, I/O bloqueada en el verificador puro, permisos, fechas históricas, corrupción, truncación, sustitución de evidencia, límites y fallos de publicación.
- 9 pruebas del cálculo de avance: un parcial no se cuenta como completo, el cierre exige aceptación registrada, se comprueban hashes de evidencia y se rechazan duplicados o referencias fuera del paquete.
- Aceptación con formato OpenSSH escrito en archivos reales y dos generaciones de log, sin arrancar un servidor. Se retiran fuente/base/política antes de verificar mediante API y CLI.
- Migración usando los archivos originales `review_credentials.py` y `case_review.py` de 0.16, commit `5187d0ab57a26ce228d24cf2f3582fd696d92a64`, con blobs comprobados. Se exportan sus filas sin modificar los payloads.
