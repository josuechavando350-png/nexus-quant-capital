# 0.16.0 — caducidad de credenciales y control persistente del reloj

Entrega exclusiva de `NQC-defensive`. El vencimiento se enlaza al registro de credenciales y al flujo de revisión existente; los permisos, casos y paquetes de evidencia conservan sus contratos.

## Comportamiento

| Operación | Regla incorporada |
|---|---|
| `set_expiry` | Fija el primer vencimiento de una credencial no revocada o acorta uno existente; no sustituye el token |
| `rotate` / `renew` | Admiten `expires_at_ns`; omitirlo o enviar `null` conserva el vencimiento anterior |
| Revisión o consulta | Rechaza la credencial cuando el reloj observado es igual o posterior a su vencimiento |
| Consulta administrativa | Distingue `active`, `expired` y `revoked`, e informa `expires_at_ns` |

`expires_at_ns` es un entero de nanosegundos desde la época Unix, mayor que cero y hasta `2**63 - 1`. No se aceptan booleanos, fracciones o fechas implícitas. Las unidades no prometen precisión de hardware de un nanosegundo.

Una fecha anterior al instante actual en `set_expiry` retira de inmediato la autorización de esa credencial. `rotate` y `renew` exigen que el vencimiento efectivo de la nueva credencial todavía esté en el futuro. Ampliar la vigencia exige una nueva credencial mediante el custodio local: `set_expiry` solo permite acortar y nunca elimina un límite existente. La rotación conserva los permisos originales y rechaza reutilizar tokens anteriores.

Los tokens anteriores sin fecha **siguen sin fecha** hasta que el custodio la configure o los sustituya por tokens con vencimiento. Esto se muestra como `expires_at_ns: null`. No se declara que todos los tokens existentes hayan quedado automáticamente limitados. No hay un proceso programado que borre archivos: la autorización comprueba el vencimiento cuando se solicita una operación.

## Transacciones y reloj

La primera fecha configurada crea una observación autenticada del reloj en la tabla aditiva `review_clock`, dentro de la misma transacción que el cambio de credenciales. No se confirma una configuración sin su registro de tiempo. Una vez activado, el control permanece para esa política/base, incluso si después se revoca la credencial que lo activó.

Antes de una operación se comprueban la cadena de credenciales y el registro HMAC del reloj. Se rechaza un instante anterior al último observado y confirmado. El registro de tiempo contiene política, checkpoint de credenciales e instante observado; una referencia inexistente, un HMAC alterado o un registro faltante bloquean la operación. Un reinicio no recrea silenciosamente el registro perdido.

La transacción usa un savepoint para separar la observación del reloj de la operación solicitada. Ante un rechazo controlado se revierte la operación y se confirma la observación previa. Si el vencimiento se observa dentro de la operación, también se conserva ese instante antes de devolver el rechazo. Por tanto, una nota insertada provisionalmente puede revertirse mientras se mantiene la observación que impide reactivarla mediante un retroceso posterior del reloj.

La revisión comprueba la vigencia al autorizar, antes de construir la entrada y después de insertarla. La consulta comprueba nuevamente antes de devolver el historial; un reintento idempotente también exige una credencial vigente. La comprobación final está dentro de la transacción, antes del commit: el reloj puede avanzar durante el commit o después de devolver los bytes. No se afirma una retirada retroactiva de resultados ya entregados.

Un error de SQLite o la terminación abrupta antes del commit puede impedir que una observación quede confirmada. En ese caso no se informa una operación exitosa ni una revocación temporal duradera. Las pruebas comprueban ambos lados del commit.

## Compatibilidad

Los cambios nuevos usan `nqc-review-credential-event-v2`, con `expires_at_ns`. El verificador conserva los registros v1 originales e interpreta sus credenciales como no limitadas temporalmente. Después del primer evento v2, rechaza volver a v1 en el mismo historial.

Los registros de revisión conservan su esquema v2 y el checkpoint de credenciales que ya incluían. Al reproducirlos, el verificador comprueba el vencimiento correspondiente a ese checkpoint y su hora registrada. Un evento anterior válido sigue siendo legible después de que venza o se revoque la credencial. No se aplica retroactivamente una fecha nueva a registros anteriores.

Todos los procesos con acceso al almacén deben actualizarse a 0.16. Las versiones anteriores no implementan estas comprobaciones. El alcance sigue siendo una base operativa y una política; no hay propagación distribuida de vencimientos.

## Uso

`tools/review_credentials.py change` acepta el campo opcional `expires_at_ns` en la petición JSON. Para asignar un vencimiento, usar `action: "set_expiry"` y omitir `--credential-file`. La petición sigue requiriendo actor, motivo, ID y el checkpoint de credenciales esperado.

Ejemplo para crear una petición que fija una hora de vigencia desde el reloj local, usando un checkpoint previamente retenido:

```python
import json
import time
from pathlib import Path

expected = json.loads(Path("checkpoint-credenciales.json").read_text())
request = {
    "actor": "analista",
    "action": "set_expiry",
    "reason": "Límite temporal aprobado por el custodio local",
    "request_id": "caducidad_001",
    "expected": expected,
    "expires_at_ns": time.time_ns() + 3_600_000_000_000,
}
Path("peticion-caducidad.json").write_text(json.dumps(request))
```

Usar el actor real configurado. Este cálculo usa la hora del equipo; no valida que sea correcta. Ejecutar la petición con los argumentos ya existentes de base, política, pin y archivo privado de administración. Conservar el nuevo checkpoint devuelto y aportarlo a `case_review.py` mediante `--credential-checkpoint`.

El vencimiento por paso del tiempo no añade automáticamente otra entrada de credenciales ni cambia su checkpoint. `status` calcula su estado usando el reloj y actualiza la observación temporal local.

## Límites de confianza

Se utiliza [`time.time_ns`](https://docs.python.org/3/library/time.html#time.time_ns), el reloj de pared local. El control detecta retrocesos respecto al registro persistido, pero no demuestra que la hora inicial sea verdadera, que avance a la velocidad correcta o que un administrador no la manipule. Congelar el reloj o restaurar conjuntamente una copia válida antigua de los datos sigue fuera de la garantía. El HMAC no constituye anclaje independiente ni protege frente al custodio de su clave.

Un salto hacia el futuro puede provocar vencimientos y bloquear operaciones cuando el reloj vuelva atrás. No se incluye un reinicio automático del registro de tiempo: borrarlo se rechaza. Falta un procedimiento de recuperación con autoridad temporal independiente y revisión de las credenciales afectadas.

Los límites existentes del historial y SQLite permanecen. Las operaciones leen cadenas y actualizan una fila temporal; no hay medición productiva de rendimiento, cuotas físicas nuevas, rotación de la clave de auditoría, identidad humana ni despliegue. El catálogo conserva 20 componentes parciales, 80 pendientes y 0 completos.
