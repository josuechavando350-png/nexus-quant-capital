# 0.18.0 — declaración firmada de validación de expedientes

`dossier_attestation` conecta el expediente de 0.17 con una firma Ed25519. El emisor reproduce primero toda la validación de evidencia, revisión, credenciales y reloj usando la clave de auditoría. Solo después firma una declaración que incluye el hash del expediente, sus pins externos, el hash de la clave pública y el informe derivado.

El receptor verifica la declaración y los bytes exactos del expediente usando una clave pública fijada fuera del documento. No recibe la clave de auditoría ni la clave privada de firma. El expediente original y sus historiales no cambian.

## Lo que verifica cada parte

| Operación | Material requerido | Resultado |
|---|---|---|
| Emitir declaración | Expediente, pins, clave de auditoría y clave privada de firma distinta | Replay completo y firma del informe resultante |
| Verificar declaración | Expediente, declaración, pins, clave pública y hashes esperados externos | Firma del emisor, vínculos del informe y coincidencia exacta de bytes |
| Repetir el replay original | Expediente, pins y clave de auditoría | Verificación HMAC completa de 0.17 |

La verificación pública devuelve `signature_verified` y `dossier_bytes_matched`. El informe incluido se llama `signer_report`: es la declaración del emisor. El resultado indica `hmac_history_replayed_by_this_verifier: false` y `report_is_issuer_assertion: true`. No se confunde posesión de una clave de firma con identidad humana verificada, verdad de los logs o custodia independiente.

Una prueba altera deliberadamente una cifra del informe y vuelve a firmarla con la clave confiable: el verificador reconoce la firma y conserva esos límites. La clave confiable puede emitir afirmaciones falsas. Este bloque reduce los secretos que necesita un receptor; no crea un testigo independiente ni protege contra un emisor comprometido.

## Firma y claves

Se usa `cryptography==50.0.2` mediante el extra opcional `signing`. No se implementa criptografía propia. La firma cubre `NQC-DOSSIER-ATTESTATION-v1` seguido de un byte nulo y los bytes JSON canónicos de la declaración. El algoritmo admitido es exactamente Ed25519; se rechazan otros nombres, firmas de longitudes diferentes y hexadecimales no canónicos.

`create_signer` crea un directorio nuevo privado y dos archivos de 32 bytes: `signing.key` y `verify.key`. La clave privada se genera con la biblioteca; la pública se deriva de ella. Antes de usar el par se comprueban permisos, tamaño, coincidencia y pin externo. La clave de firma debe diferir de la clave de auditoría. La clave privada se guarda sin cifrado en un archivo de modo 0600 dentro de un directorio 0700; no hay KMS, HSM ni separación de cuentas del sistema operativo.

La creación no reemplaza un directorio existente. Un fallo entre la escritura de ambos archivos deja una inicialización incompleta que se rechaza; no se adopta ni se borra automáticamente. El operador debe conservar o revisar ese directorio y escoger una ruta nueva para otro intento.

El receptor debe obtener la clave pública y su hash por un canal confiable independiente del archivo recibido. Tomar un pin del propio documento no establece confianza. Los hashes esperados de expediente/declaración y los checkpoints también se aportan externamente. No hay descubrimiento automático de claves, rotación, revocación, vencimiento de firma ni lista de confianza distribuida.

## Uso

Desde `migration/defense`, instalar el extra en el entorno de ejecución elegido:

```bash
python3 -m pip install '.[signing]'
python3 -B tools/dossier_attestation.py init-signer --help
python3 -B tools/dossier_attestation.py issue --help
python3 -B tools/dossier_attestation.py verify --help
```

- `init-signer`: exige `--signer-root`; devuelve el hash de la clave pública y no imprime la privada.
- `issue`: exige `--signer-root`, `--audit-key-file`, `--pins-file`, `--dossier-file`, `--dossier-digest`, `--public-key-digest` y `--output`.
- `verify`: exige `--public-key-file`, `--public-key-digest`, `--pins-file`, `--dossier-file`, `--dossier-digest`, `--attestation-file` y `--attestation-digest`. No acepta parámetros de claves privadas o de base operativa.

El archivo de pins mantiene exactamente el formato de 0.17. La CLI devuelve JSON y código 2 para rechazos controlados. El motor base conserva sus dependencias vacías; el extra se necesita para este bloque y para ejecutar la suite completa a partir de 0.18. Si falta la biblioteca, la operación de firma devuelve `attestation_dependency_unavailable`.

## Publicación local e invariantes

La declaración se escribe en un directorio privado, sin reemplazar contenido diferente, y se relee y verifica antes de confirmar éxito. Firmar el mismo expediente con los mismos pins y clave produce el mismo resultado: un reintento puede recuperar una publicación previa sin reemplazarla. La declaración incluye notas y datos del caso; que su firma sea verificable con clave pública no autoriza divulgar su contenido.

Se aceptan como máximo 16 MiB de declaración y 32 MiB de expediente. No hay red, consulta de reloj ni acceso a la base en el verificador puro. La CLI lee únicamente los archivos explícitos. El receptor no abre rutas incluidas en el expediente.

Una declaración antigua sigue verificándose para sus pins originales después de reabrir un caso. No acredita el estado actual ni una hora independiente. No se activan producción, servicios, workflows ni respuesta sobre activos.

## Evidencia ejecutable

```bash
python3 -B -m unittest discover -s tests -p test_dossier_attestation.py -v
python3 -B tools/check_dossier_attestation.py
```

Las 34 pruebas nuevas cubren la firma y sus vínculos, ausencia de E/S en el verificador puro, cambios de contenido, sustitución de claves, pins de otro ámbito, límites, permisos, publicación concurrente/reintentable, fallos de lectura/escritura, inicialización incompleta, confianza en el emisor y CLI sin secretos. Se contrasta también el vector público TEST 1 de RFC 8032; la clave publicada en ese vector se usa exclusivamente en esa prueba.

La aceptación usa registros OpenSSH RFC3339 redactados para la prueba y archivos/SQLite/claves reales. Recorre detección → evidencia → revisión → expediente → declaración. Retira logs, base, política y archivos de claves privadas antes de ejecutar la verificación en un proceso nuevo. No se arrancó un daemon SSH ni se usó tráfico productivo.

`SIGNING_PACKAGE_CHECK.json` registra la instalación sin red ni resolución de dependencias en un directorio temporal, la importación del paquete instalado, firma con el backend existente y la importación del motor base sin paquetes de terceros. No equivale a una instalación en otra máquina.

`DOSSIER_ATTESTATION_CHECK.json` conserva cinco criterios del bloque y sus resultados. La entrega amplía C048/C050 dentro de su alcance parcial; no incrementa el número de componentes completamente aceptados ni cierra C093, cuya rotación de claves sigue pendiente.
