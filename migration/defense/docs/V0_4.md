# 0.4.0: auditoría paginada con checkpoint final fijo

La exportación completa conserva sus límites anteriores. El formato nuevo `nqc-audit-page-v1` permite recorrer historiales mayores en bloques limitados por registros y tamaño, sin cargar el historial completo en una lista. Exportador, verificador, consumidor local y CLI comparten la misma cadena HMAC y reproducción de recibos.

Cada página contiene un checkpoint inicial, un objetivo final, el último checkpoint de sus registros y hasta un registro anterior de contexto. Este contexto permite validar un `snapshot_authorized` cuyo recibo quedó en la página precedente. Se autentica contra el checkpoint inicial y su recibo se reproduce antes de aceptar el snapshot. El contexto no incrementa los contadores del recorrido.

`Engine.export_page` exige checkpoints inicial y final explícitos. La consulta SQLite selecciona registros posteriores al inicial y hasta el final; nuevos eventos no desplazan ese objetivo. Los checkpoints deben seguir disponibles con el mismo hash en la base. Cada llamada verifica también el ledger completo antes de exportar. Se garantiza progreso o un rechazo explícito si el presupuesto no permite incluir el próximo registro y el contexto.

`verify_page` verifica un intervalo. `AuditPageVerifier` compone intervalos consecutivos: no avanza ante un fallo, rechaza páginas repetidas o fuera de orden y no permite `finish` antes del objetivo. El fin de una página parcial nunca se presenta como el fin del historial solicitado. Reanudar desde un checkpoint intermedio declara `from_genesis: false`; el intervalo anterior requiere su propia evidencia.

Límites: 512 registros nuevos y 1 MiB de JSON por página; el verificador rechaza archivos ZIP mayores de 2 MiB. La API permite reducir el presupuesto hasta 1 KiB. El formato anterior y el paginado comparten comprobación de registros, recibos y vínculo de snapshots. Los contenidos de los artefactos y tokens no se incorporan a las páginas.

La CLI local `export-page` lee `--target` desde un archivo de checkpoint confiable y, al reanudar, `--start` desde el resultado previamente verificado. Devuelve el siguiente checkpoint y crea la página sin sobrescribir archivos. `tools/verify_audit_pages.py` recibe los archivos en orden, `--key-file`, `--policy-digest`, `--target` y opcionalmente `--start`; solo devuelve éxito cuando completa el intervalo. No hay endpoint HTTP nuevo ni envío externo.

Validación: 25 pruebas nuevas, 148 pruebas del paquete y 9 de aislamiento. Cubren cortes en cada posición de un ciclo de consumo real, páginas omitidas/repetidas/reordenadas, truncamiento, autenticación, replay del contexto, tamaños, checkpoint final perdido, corrupción fuera del bloque, reanudación tras abrir nuevamente SQLite, eventos posteriores y CLI. El manifiesto real de NQC se verifica en tres páginas. El control de volumen valida 10.003 registros en 20 páginas: tres de una admisión real local y 10.000 marcadores sintéticos identificados como carga de prueba.

Límites pendientes: no se compacta ni borra la base, no hay anclaje independiente y cada página requiere verificar el ledger completo. La prueba de volumen no mide rendimiento productivo. Un operador que seleccione un checkpoint antiguo solo solicita verificación hasta ese punto. Las claves HMAC y el proceso local mantienen el mismo modelo de confianza de las entregas anteriores.
